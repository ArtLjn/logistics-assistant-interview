# 物流检索与异常排查助手

仓库员工通过自然语言查询操作规范和订单状态。实现一个本地助手，由 Agent 决定查 SOP、查订单或两者都查。RAG 从本次召回的 SOP 片段与订单字段组织回答。

## 实现要求

1. **SOP 检索。** 实现 `search_sop(query)`，从 47 条语料中召回最多 3 条，保留 `id`、`title`、`text`。覆盖口语问法，区分入库差异、盘点差异、出库实拣差异和退货差异。同义词放在 `data/synonyms.json`，仅用于查询归一化，不得映射到片段 ID 或答案。可选用关键词检索、BM25、向量或混合方案，评分口径一致。
2. **RAG 回答。** 召回片段要进入回答上下文，引用 ID 要能回指检索记录，`excerpt` 必须是片段中不超过 120 字的连续原文。证据不足时说明“现有数据无法确认”。不得用整份 SOP 代替检索、写死验收答案或凭模型知识补充事实。
3. **查订单。** 实现 `query_order(order_id)`，按完整单号精确查询，返回 `order_id`、`found`、`order_status`、`warehouse`。查不到时 `found` 为 `false`。订单状态能确认进度，具体原因须进一步核实。
4. **路由与接口。** 流程问题检索 SOP，纯状态问题只调用订单工具，结合订单排查时先查订单再结合状态检索 SOP。记录每一步调用，同一问题重复提问结果一致。按 [API 契约](api.md) 实现 `POST /ask`。
5. **前端。** 在 `web/index.html`、`web/app.js`、`web/style.css` 中使用原生 JavaScript 和 `fetch`。支持提交、显示回答原文、逐条展示引用、折叠展开 trace、加载和错误提示。刷新后可继续提问。

## 运行与交付

- 后端二选一。Python 3.11 + FastAPI，或 Java 17 + Spring Boot 3.2（Maven）。
- 监听 8000 端口，单进程离线运行。可用本地 JSON 或 SQLite，订单不进 SOP 索引。原始 SOP 和订单业务字段作为给定数据。交付检索索引，并提供一条命令在索引删除后重建。
- 模型可选。设置 `AGENT_LLM=off` 后仍须通过验收。关闭模型时用固定模板拼接本次片段和订单字段。
- 可以用本地检索库或 SQLite FTS。使用 Elasticsearch 时，将它并入同一启动命令，预置镜像和索引，确保断网可起。其余方案无需额外服务。
- 启动和测试各一条命令，放在 README 首屏。候选人若引入额外依赖，须在验收前一并备好离线依赖。
- README 还须包含可复制的 `/ask` 请求、片段索引与召回排序说明、一次误判调优、`AGENT_LLM` 开关、一处亲自检查或修正的 AI 生成代码、上游合并说明与已知限制。

## Git 协作与提交

1. 从 `exam-base` 创建 `feature/assistant`，按 README 将 `exam-conflict` 快进到功能分支。这一步带入模拟的 JSON 排版改动，保留原始字段与文字，确保后续会遇到题面要求的冲突。
2. 开发都在功能分支上完成。自行提交至少 6 次，每次一个目的，起步提交与上游提交不计入。提交前检查密钥与构建产物。
3. 核心链路跑通后，将 `origin/main` 合进功能分支。`main` 新增订单 `HD202611005`，并在 `TRA-02` 末尾追加“升级异常前，须先记录最后有效扫描站点。” 解决 `data/sop.json` 冲突时保留双方变更，更新索引，复测新增订单、新条款和一条原有用例。
4. 保留 `main` 和 `feature/assistant`。将仓库链接发给面试官，或在离线环境运行 `git bundle create submission.bundle main feature/assistant exam-base`，提交生成的文件。
